Chapter 4 — Bytecode (Deep Dive)

==================================================
1. Interview Answer
==================================================

Bytecode is the platform-independent intermediate instruction set generated by
the Java compiler (javac). It is stored in .class files and executed by the JVM,
which interprets or JIT-compiles it into native machine code.

Flow:

Java Source (.java)
        |
      javac
        |
Bytecode (.class)
        |
      JVM
        |
 Native Machine Code

==================================================
2. Why Bytecode?
==================================================

Without bytecode, Java programs would need to be compiled separately for every
operating system.

Benefits:
- Platform independence
- Security through bytecode verification
- JIT optimization
- Smaller deployment artifacts

==================================================
3. Bytecode is Stack-Based
==================================================

Unlike many CPUs, JVM bytecode uses an operand stack.

Example Java:

int c = a + b;

Typical Bytecode:

iload_1
iload_2
iadd
istore_3

Execution:

Stack:
[]
[a]
[a,b]
[a+b]
[]

==================================================
5. Viewing Bytecode
==================================================

Compile:
javac Hello.java

Disassemble:
javap -c Hello

This prints JVM instructions for every method.

==================================================
6. Bytecode Verification
==================================================

Before execution the JVM verifies:

- Valid instruction format
- Stack safety
- Type safety
- Illegal memory access
- Invalid jumps

This is a major security feature.

==================================================
7. Constant Pool Usage
==================================================

Bytecode references entries in the Constant Pool instead of embedding repeated
strings, method names, or class names directly.

Example:
"Hello World"
System.out.println
java/lang/Object

==================================================
8. JIT Interaction
==================================================

Initially:
Bytecode is interpreted.

Hot methods:
↓
JIT Compiler
↓
Native Machine Code

Benefits:
- Faster execution
- CPU-specific optimizations
- Inlining
- Dead code elimination

==================================================
9. Production Example
==================================================

A Spring Boot REST endpoint may execute millions of times per day.

The JVM identifies it as hot code and JIT-compiles it, significantly reducing
CPU usage and response time.

10. Interview Questions
==================================================

Q. Is bytecode machine code?
A. No.

Q. Who executes bytecode?
A. JVM.

Q. Why doesn't Java compile directly to machine code?
A. Bytecode enables portability and runtime optimization.

Q. Which tool displays bytecode?
A. javap -c

Q. What is invokedynamic primarily used for?
A. Dynamic language support and Java lambda implementation.

==================================================
11. Senior Cross Questions
==================================================

Q. Why is the JVM stack-based instead of register-based?

Answer:
A stack-based instruction set is simpler, portable across CPU architectures,
and results in a compact bytecode format. The JIT later maps it efficiently to
register-based native instructions.

Q. Can bytecode be modified?

Answer:
Yes. Libraries like ASM, Byte Buddy, and Javassist can generate or modify
bytecode at runtime. Popular frameworks such as Spring, Hibernate, and Mockito
use this capability.

==================================================
12. Common Mistakes
==================================================

- Confusing bytecode with native code.
- Thinking the CPU executes .class files directly.
- Ignoring bytecode verification.
- Assuming interpretation is always used.
