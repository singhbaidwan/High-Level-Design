CHAPTER 16 – POLYMORPHISM
==================================================

Definition:
Polymorphism means "many forms". The same interface or method call can exhibit
different behavior depending on the actual object.

Types:
1. Compile-time (Method Overloading)
2. Runtime (Method Overriding)

Example:

class Animal {
    void speak() { System.out.println("Animal"); }
}

class Dog extends Animal {
    @Override
    void speak() { System.out.println("Bark"); }
}

Animal a = new Dog();
a.speak(); // Bark

Interview Points:
- Overloading is resolved at compile time.
- Overriding is resolved at runtime using Dynamic Method Dispatch.

==================================================
CHAPTER 17 – ABSTRACTION
==================================================

Definition:
Abstraction hides implementation details while exposing only essential behavior.

Ways to achieve:
- Abstract Classes
- Interfaces

Benefits:
- Loose coupling
- Easier maintenance
- Better extensibility

Real-world Example:
A payment service exposes processPayment() without exposing gateway-specific
implementation.

==================================================
CHAPTER 18 – INTERFACE vs ABSTRACT CLASS
==================================================

Abstract Class
- Can have constructors
- Can have state (instance variables)
- Can contain abstract and concrete methods
- Supports partial implementation

Interface
- Defines a contract
- Multiple interfaces can be implemented
- Supports default and static methods (Java 8+)
- Ideal for capabilities (Runnable, Comparable)

Interview Question:
When to use Interface?
- Multiple implementations
- Loose coupling
- API contracts

When to use Abstract Class?
- Shared state and common implementation

CHAPTER 19 – COMPOSITION vs INHERITANCE
==================================================

Inheritance (IS-A)

Car extends Vehicle

Composition (HAS-A)

Car
 └── Engine

Why Composition is Preferred:
- Lower coupling
- Better flexibility
- Easier testing
- Runtime behavior changes

Interview Tip:
Prefer composition unless there is a strong IS-A relationship.

# Node Structure

Internally every entry looks like

```java
static class Node<K,V>{

    final int hash;

    final K key;

    V value;

    Node<K,V> next;

}
```

Let's understand why every field exists.

---

## hash

```
final int hash;
```

Question

Why not calculate hash every time?

Answer

Because hashCode() can be expensive.

Instead HashMap computes it once.

Stores it.

Reuses it.

Avoids repeated calculations.

---

## key

```
final K key;
```

Marked final.

Why?

Changing key after insertion breaks lookup.

Therefore HashMap doesn't allow replacing key.

Only value changes.

---

## value

```
V value;
```

Notice

Not final.

Because

```
map.put("A",10);

map.put("A",20);
```

Key stays same.

Value changes.

---

## next

```
Node next;
```

Collision handling.

Suppose

```
capacity =16

Key A

↓

bucket 5

Key B

↓

bucket 5
```

Now

```
Bucket 5

↓

Node A

↓

Node B

↓

Node C
```

That's why every Node stores next.

# Computing Hash

Suppose

```
key=10
```

Java calls

```
hashCode()
```

For Integer

```
10
```

Now Java performs

```java
h ^ (h >>> 16)
```

Question

Why?

Because

Suppose hashCode only changes upper bits.

Lower bits remain identical.

Without mixing

Many collisions happen.

So Java mixes upper bits.

---

Example

Suppose

```

1111111100000000
```

After spreading

```
11111111

XOR

0000000011111111

↓

Better distribution
```

This is called

Hash Spreading.

Because

Suppose

# Interview Cross Question

Interviewer

Historically many hash tables use primes.

Java chooses

Power of 2

Bit masking

The hash spreading step compensates for potential bias.
